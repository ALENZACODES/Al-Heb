## What this does not show (read this before trusting the numbers)
Only a real phone and a real screen reader can verify: how VoiceOver (iOS), TalkBack (Android) and NVDA/JAWS actually read each screen (axe checks names, roles and structure, not whether the reading order and wording make sense); whether the Hebrew is pronounced as Hebrew by the screen reader's voice; swipe-navigation order; whether the bottom tab bar and More sheet are reachable one-handed and not hidden by the home indicator or browser chrome (`env(safe-area-inset-bottom)` is used but only seen in an emulator); touch target comfort for real fingers; zoom to 200-400% and large system text on a device; Windows high-contrast / forced-colors mode (a `forced-colors` rule exists, never looked at); reduced-motion behaviour on a device; whether the tracing animation is understandable without sight (it is not, see below). Automated axe rules cover roughly a third of WCAG issues. Contrast was measured by axe in light and dark, but not for text drawn on images or canvas.
No screen reader, no iOS device, no Android device was used for any result in this file.

## Stroke tracing: is there a way to learn without drawing?
Only one routed screen traces strokes: Letters (`/letters/:id`, `src/letters/trace.view.js`). Findings:
- The tracing surface is a pointer-only SVG (pointer events; no focusable element, no key handler). A learner who cannot draw can press **Animate** (plays the stroke order) and **Hint**, can read "Remember it" (shape, sound, story), use the Atlas and the Typing tab, but **cannot register the strokes, so the letter is never marked completed**. Nothing else in the app is gated on that completion (checked: `letters/progress.js` is read only by the letters view), so the learner is not blocked, only unable to earn the tick.
- Animate is visual only. A blind learner gets "Tracing area for Alef" and no description of the stroke order.
- Tab order: the Animate button is the 45th Tab stop on the page (every letter in the grid is a stop). A roving tabindex (arrow keys inside the grid) would cut this.
- The word-tracing screen being built by another lane (`src/wordtrace/wordtrace.view.js`, not yet routed in `router.js`, so not covered by axe) already has the right design: a "Show me, stroke by stroke (buttons)" mode with a **Next stroke** button that calls `tracer.submit(median)`, and it says honestly that an assisted round does not move the guide forward.
**Spec for the Letters view (lane 2, not done here because the file is not in this lane):** (1) add the same "Show me, stroke by stroke (buttons)" toggle and **Next stroke** button using `tracer.submit(block.strokes[state.index].median)` (the controller already documents `submit` as "assistive input"); (2) record an assisted completion separately (`assisted: true`) so the tick means "walked through", not "drew it"; (3) put `aria-live` text on the stroke counter ("Stroke 2 of 3 done"); (4) give each letter a one-sentence stroke description for screen readers ("Alef: three strokes. First the long diagonal from top right to bottom left, then ...") which needs a native-teacher check like the rest of the draft stroke data; (5) roving tabindex on the letter grid.
