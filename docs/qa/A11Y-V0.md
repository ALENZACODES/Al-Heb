# Accessibility pass on the 15 v0 routes (375x667)

Observed only. Run on 2026-11-04 with Chromium (Playwright) against the working tree, served by `tools/serve.mjs`, 375x667 at device scale 2, touch on. A throwaway script (not kept in the repo) visited each route with a profile that had `onboarded: true` and no lesson progress. No screen reader, no real phone, no iOS or Android device, no Windows high-contrast session was used for anything below. Automated checks cover only part of what matters; treat this as a list of what a script saw.

Routes (every route with `tier: 'v0'` in `src/shell/router.js`): `/`, `/learn`, `/letters`, `/letters/atlas`, `/letters/bet`, `/progress`, `/firstday`, `/install`, `/credits`, `/privacy`, `/offline`, `/settings`, `/welcome`, `/search`, `/about`.

## What was checked, and what was seen

| Check | Method | Seen |
|---|---|---|
| Accessibility-tree snapshot per route | `locator('body').ariaSnapshot()` | Taken for all 15 (31 to 404 lines each). Read in part (home in full), not line by line for every route. Home has navigations "Main", "Go to" and "More ways to learn"; every other route has "Main" only. Skip link is first, then banner, nav, the "Sound status" and "Audio status" regions, then main. |
| Hebrew has `lang="he"` and `dir="rtl"` | every visible element whose own text contains Hebrew letters: nearest `[lang]` must start `he`, computed `direction` must be `rtl` | 0 offenders on all 15 routes (3 to 74 Hebrew-bearing elements per route; /learn 74, /letters 35, atlas 34, home 13). Mixed Latin/Hebrew elements were counted too. Hidden elements and Hebrew inside `aria-label` text were not checked. |
| Headings | levels of all visible headings in DOM order | Exactly one `h1` on every route; no skipped level (h1 then h2 then h3 only). /letters, /letters/atlas, /letters/bet have a visually hidden `h1` added by the shell. |
| Landmarks | element counts | 1 `main` everywhere, 1 `nav` "Main" (home 3), a banner. No `footer`/contentinfo on any route (none exists in the app). /privacy counts 2 `header` elements because a card uses `<header>`; the snapshot shows 1 banner. |
| Names on icon-only controls | visible `button`, `a[href]`, inputs, `summary` with no text, label, `aria-label`, `title` or image alt | 0 unnamed controls on all 15 routes. axe `button-name`, `link-name`, `label` also clean. |
| Live regions | `[aria-live]`, `role=status/alert/log` per route; behaviour below | Shell has a polite route announcer (`#announcer`, set to the page title on each route change), the sound status, update and storage banners. Quiz feedback: see "Interactions". |
| Focus after route change | in-app hash change from home, 5 routes, plus a tap on the Learn tab | Focus lands on the new `h1#view-title` each time (6 of 6, with a 500 ms wait after the first navigation measured; one earlier read taken before the Learn module had finished loading showed `body`, so a slow first load can leave focus on `body` for a moment, not re-measured under throttling). |
| `prefers-reduced-motion` | emulated `reduce`: running CSS animations, non-zero animation/transition durations, `scroll-behavior` | 0 running animations, 0 non-zero durations, `scroll-behavior: auto` on all 15 routes. Letter-trace "Animate" is JS-driven (not CSS): it ignored the preference before the fix, see below. |
| Dark mode | axe 4.14.0 with `colorScheme: dark` | 0 violations on 13 routes; 1 minor on /settings (below). |
| Light mode | axe, same | same as dark. |
| Forced colors | `forcedColors: 'active'` emulation, axe, and a screenshot of `/` | axe reports `color-contrast` (serious) on the primary button of 7 routes (`/`, /learn, /progress, /offline, /settings, /welcome, /about) as fg #fffaf0 on #ffffff. The screenshot of `/` shows the button drawn in system colours with a 2px border and legible text, so this looks like axe reading author colours that forced colors replaces; only `/` was looked at, the other six were not. A real forced-colors device was not used. |
| Text at 200% | `html{font-size:200% !important}` (rem-based text scales; fixed-px text does not, which is how a browser default-size setting behaves, not how Android system font scaling behaves) and a check for horizontal overflow and clipped or off-screen text | No page-level horizontal overflow on any route. Clipping and cut-off content found on 3 routes before the fixes (below). The bottom bar labels are capped at 14px on purpose (`app.css`), so Learn / Progress stay small at 200% while More grows. |
| Tap targets | bounding box of every visible `a[href]`, button, input, select, summary, `[role=tab]`: under 44 in either dimension | See below. |

## Interactions (before any fix, by script)

| Where | Action | Observed |
|---|---|---|
| /firstday quick check | focus a choice, click | Feedback is announced (`role=status`: "Not quite: it is Shin. Nothing is lost."). The three choice buttons become `disabled`, so the focused button loses focus and `document.activeElement` becomes `body`; it stays `body` after the screen re-renders (immediately after the last question, after 0.5 to 1.5 s between questions) until Next is pressed. After Next, focus goes to the new `h1`. |
| /learn Mark complete (r01) | click | Focus becomes `body`. The "1 / 71 lessons done" and "6 reviews due" paragraphs are `role=status`. |
| /learn?review=1 | Show answer | Focus moves to the answer block (`.alef-answer`). |
| /learn?review=1 | grade "1 Again" | Feedback "That one will come back soon." is in a status region; focus becomes `body`. |
| /letters/atlas | Quiz, then a tile | Focus stays on "Stop quiz", then stays on the pressed tile; "That is Alef." is announced via `role=status`. |
| /letters/alef | Animate, reduced motion | Before: strokes swept progressively (102 path updates over 3.5 s) with the preference set to `reduce` as well as without. After: 3 path updates (one finished stroke each), same feedback text. |
| Home streak | read structure | "Streak: ..." is a plain paragraph in the "Today's lesson" region; it is built when Home loads and has no live region. Nothing announces a streak change while it is on screen, and Home is not on screen when the day is counted (study happens on other routes), so no streak announcement exists anywhere. Not changed. |

## newviews re-run after the fixes (2026-11-04, late)

`node tools/a11y/newviews.mjs --routes <the 15 v0 routes>` (390px, light and dark; Chromium only, no screen reader, no device). Of the 9 findings listed above (focus left on `body` on `/`, reflow at 320 and 195px on `/`, the two backwards focus jumps on `/letters` and `/letters/bet`, the `/settings` wipe input at 195px), 0 remain: the run reports no focus, reflow, focus-order or overflow finding on any of the 15 routes. The run reported 7 findings of a different kind, `page-error` (one console message "Failed to load resource: 404" each, on `/letters`, `/letters/atlas`, `/letters/bet` in light and dark, and `/firstday` in light). A separate load of `/letters` and `/firstday` with a response listener showed no 4xx response, so the URL that returned 404 was not identified and the 7 are not explained or fixed. The earlier 9 therefore went to 0, but the run as a whole is not clean.
