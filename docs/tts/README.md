# Local TTS factory for the Israeli-Hebrew clips

Status: the pipeline is built and its plumbing is tested in `--mock` mode. **No real Hebrew clip has been generated by it yet**, and no model quality has been checked. Nothing here has been listened to.

What it does: turns the audio manifest into a render plan, renders the Israeli-tradition clips on your own machine with an open-weights model, polishes them, runs an automatic acceptance gate, and marks only the accepted clips in the manifest as synthetic (`status: "tts"`). Sephardi and Ashkenazi clips, and Israeli letters, vowels and syllables, are never synthesised: they stay human-only.

## What goes where

| Step | Tool | Input | Output |
|---|---|---|---|
| 1 plan | `tools/tts/plan.mjs` | `data/audio/manifest*.json`, `data/vocab/deck-order.json`, `data/vocab/frequency.json` | `tools/tts/plan.json`, `tools/tts/donor-export/human-only-<tradition>-<voice>.csv` |
| 2 render | `tools/tts/render_chatterbox.py` | `plan.json`, reference WAVs for the m and f voices | `<work>/raw/<voice>/<tradition>/<kind>/<id>.wav` |
| 3 post | `tools/tts/post.mjs` | the WAVs | `<work>/mp3/audio/<voice>/<tradition>/<kind>/<id>.mp3` |
| 4 verify | `tools/tts/verify.py` | the MP3s | `tools/tts/verify-report.csv` |
| 5 mark | `tools/tts/manifest_update.mjs` | the report, the MP3s | copies accepted MP3s to `audio/`, writes `<clip>.mp3.meta.json`, sets `status: "tts"` in the manifest |
| all | `tools/tts/run_all.sh` | | runs 1 to 5; `--mock --root <scratch copy>` for a dry run (it refuses `--mock` without `--root`) |

`<work>` is `$ALEF_TTS_WORK` or `~/alef-tts-work`. It is outside the repo on purpose (raw WAV is large).

Priority order in the plan: tier 1 core prayer lines (same list as the human-recording priority subset), tier 2 words in `deck-order.json` (by position), tier 3 words or lines found in `frequency.json` (by corpus rank), tier 4 the rest. As of the last run the plan held 4,860 Israeli clips (both voices) and 9,176 human-only entries; re-run `plan.mjs` for current numbers. Entries that already have a file (human or tts) are never planned.

## Install (your machine)

You need: Python 3.10 or newer (3.11 is the safe pick; versions were not tried here), Node 20+, ffmpeg and ffprobe on PATH.

```bash
python3.11 -m venv ~/alef-tts-venv && source ~/alef-tts-venv/bin/activate
pip install chatterbox-tts faster-whisper nakdimon      # nakdimon only if you need --vocalize
# NVIDIA GPU: install the CUDA build of torch first, per pytorch.org. Apple silicon: --device mps. CPU works, slowly.
```

Version note (verified from the fetched pages): the Chatterbox README on GitHub describes a "Multilingual V3" checkpoint selected with `t3_model="v3"`. The PyPI release `chatterbox-tts 0.1.7` inspected here only loads the v2 checkpoint (`t3_mtl23ls_v2.safetensors`). The renderer detects whether `from_pretrained` accepts `t3_model` and uses v3 if so, otherwise v2, and records which in `render-log.jsonl`. To get v3 you may need `pip install git+https://github.com/resemble-ai/chatterbox` (not tried).

### Voices

Chatterbox clones the voice in a reference WAV. Provide one for each of the two narrator voices (about 10 to 20 seconds of clean speech, no music):

```bash
--ref-m ~/voices/m.wav --ref-f ~/voices/f.wav
```

Use only a voice you own or a donor who signed `docs/voices/donor-rights-grant.md`. Without references the renderer refuses to run (both voices would sound the same) unless you pass `--allow-default-voice`.

## Run

```bash
cd alef
node tools/tts/plan.mjs                                    # writes plan.json + donor-export/
python3 tools/tts/render_chatterbox.py --limit 50 --ref-m ~/voices/m.wav --ref-f ~/voices/f.wav   # first 50 only
node tools/tts/post.mjs --limit 50
python3 tools/tts/verify.py
node tools/tts/manifest_update.mjs --dry-run               # then without --dry-run
node tools/audio/build_manifest.mjs --check                # must still say "manifest files are current"
```

Listen to a sample before scaling up. Follow `docs/voices/tts-evaluation-protocol.md` (native Hebrew listeners, blind, pointed vs unpointed). The gate below does not replace this.

Everything is resumable: re-running skips WAVs and MP3s that exist. Delete a file to redo it. Add `--vocalize` to the render step only if some plan text has no niqqud (Nakdimon adds it; the manifest text normally already has niqqud).

Not measured: no real model has run in the sandbox where this was built. A real-model attempt was made on 2026-11-04 and failed for resources, not for access: PyPI and Hugging Face were reachable (the Chatterbox weights file is about 2.1 GB), CPU torch installed, but `pip install chatterbox-tts faster-whisper` ran out of disk (about 11 GB free, 2 CPUs, 7 GB RAM, no GPU) after 6.5 minutes. Nothing was generated or transcribed. Chatterbox is a 0.5B-parameter model; on a recent NVIDIA GPU, short words are commonly a second or two each, so a few thousand clips would be a few hours. On CPU expect many seconds per clip, so a day or more for the full plan. Post-processing took roughly 1 to 2 s per clip on a slow 2-core sandbox; `post.mjs --jobs N` parallelises it. verify.py with Whisper large-v3 is fast on GPU and slow on CPU (use `--model small` to trade accuracy for speed, and expect more rejects).

## The acceptance gate

`verify.py` transcribes each MP3 with faster-whisper (`large-v3`, language `he`), removes niqqud and punctuation from both target and transcript, folds final letters, ignores spaces, and computes character error rate. CER above 0.10, a clip under 0.2 s or over 20 s, or an empty transcript is rejected. Rejected clips are listed in `tools/tts/verify-report.csv` with the reason and are never marked.

The gate catches missing, truncated, repeated or wrong speech. It does **not** check vowels (the transcript has no niqqud), accent, stress or voice quality, and Whisper itself makes mistakes on short isolated words, so some good clips will be rejected and some bad ones accepted. Spot-check by ear.

## MP3 format and metadata

Mono, 44.1 kHz, 64 kbps CBR, loudness normalised in two passes to -16 LUFS integrated (true peak limit -1.5 dBTP), leading and trailing silence trimmed (about 50 and 80 ms kept). Metadata: `-map_metadata -1`, no ID3v1/v2, no Xing/Info header, bitexact flags. `post.mjs` then runs ffprobe on every output and rejects the file if any tag exists, if there is more than one stream, or if the channel count or rate is wrong. It also zeroes the encoder version string that libmp3lame writes into frame padding ("LAME3.100"); that is only done with `-reservoir 0`, and the script compares the decoded samples before and after and refuses the clip if they differ (checked on mock tones in this sandbox, not on speech).

One thing cannot and should not be stripped: Chatterbox embeds an inaudible neural watermark (Resemble's PerTh) in every output; its README says it survives MP3 compression. This is a machine-detectable "generated" marker and is consistent with labelling the clips as synthetic. Do not try to remove it.

## How the app labels these clips

`manifest_update.mjs` writes `status: "tts"` and `source: "tts:chatterbox"` into the manifest entry (core file or word shard), plus a sidecar `audio/.../<id>.mp3.meta.json` (`status: "tts"`, `redistributionCleared: false`, CER, render time). `tools/audio/build_manifest.mjs` reads that sidecar, so a later rebuild gives the same result. It never writes `"recorded"` and never changes an entry that is already `"recorded"` (a human clip).

Status naming decision: the value stays `tts` (no rename to `recorded-tts`; see the deviation note below). What changed instead is the wording: every place that shows a status reads one table, `src/shell/audio-labels.js`: `recorded` = "Recorded by a human reader", `tts` = "Synthetic voice (Israeli only), not a recorded teacher", `missing` = "No audio yet". `describeResult` in `src/shell/audio.js`, `audioAccess` in `src/shell/audio-access.js`, the exercise, vocabulary, theme and Torah-reading screens, and the generated `docs/voices/coverage.md` (`tools/audio/coverage.mjs`) all use it; `tests/audio.labels.test.js` greps `src/` for the old ad-hoc phrasings. Do not add a status that the app does not know.

**Deviation from the brief:** the brief asked for the status `recorded-tts`. I did not use it, because with the current code it would be wrong in three ways: `summarizeManifest` counts any status other than `recorded` or `tts` as missing; `fileLabel` would label the clip as a human recording (the opposite of honest); and `build_manifest.mjs` only accepts `tts` or `recorded` from a sidecar, so a rebuild would turn it into `recorded`. `tts` is already distinct from human. If you want a new name, `src/shell/audio.js`, `src/shell/audio-labels.js`, `src/audio/player.js`, `tools/audio/build_manifest.mjs` and `tools/audio/coverage.mjs` all need to change together.

## Handing clips back

Same machine as the repo: `manifest_update.mjs` copies the accepted MP3s into `audio/` itself. Then run `node tools/audio/build_manifest.mjs --check`, review, commit (this tool commits nothing), and run the precache build as your normal release step needs.

Different machine: zip `<work>/mp3/audio` and `tools/tts/verify-report.csv`, unzip the MP3s into a scratch folder on the repo machine and run

```bash
node tools/tts/manifest_update.mjs --work <scratch-parent> --report <path>/verify-report.csv
```

where `<scratch-parent>/mp3/audio/...` holds the files (the tool looks for `<work>/mp3/<manifest path>`). There is no separate audio ingest tool in the repo (`tools/images/ingest*.mjs` is for images), so this is the hand-back path.

Human-only work: `tools/tts/donor-export/human-only-<tradition>-<voice>.csv` uses the same columns as `docs/voices/recording/recordings_needed.csv`, so it can feed the existing donor sheet tooling (`tools/audio/recording_sheets.mjs` reads the priority subset of the same data).

## Traps list (per earlier research, re-verify before shipping)

These come from the project's earlier research notes and from the brief. **They were not re-checked in this session.** Treat each as a warning to verify at the primary source, not as a finding.

- CapCut voices and clones: terms for commercial use of generated audio and of voice clones; per earlier research, restrictive. Re-verify.

- Edge-TTS (the unofficial client for Microsoft's browser voices): per earlier research, not a licensed route for redistributing audio. Re-verify.
- Azure free tier (F0): per earlier research, restrictions on commercial use and redistribution of output at the free tier. Re-verify, together with the Azure and Google output-redistribution question already recorded in `docs/voices/tts-evaluation-protocol.md`.

## Tests

`node --test tests/tts.pipeline.test.js` runs plan, render, post, verify and manifest update end to end in `--mock` mode on 20 clips (one rendered with the wrong tone) in a temporary directory. It asserts: the wrong clip is rejected and stays `missing`; 19 are marked `tts`; a pre-existing human `recorded` clip, an Ashkenazi entry and an Israeli letter entry are untouched; every MP3 passes the ffprobe metadata check; loudness lands within 1.5 LU of -16 on a sample; both render and post are resumable; and the manifest is not touched without `--allow-mock`. Mock mode proves the plumbing and the gate logic only: the "voice" is a sine tone and the "transcription" reads the tone's frequency back to the text. It says nothing about Chatterbox, Whisper or Hebrew quality. The test takes over a minute in a slow 2-core sandbox.
